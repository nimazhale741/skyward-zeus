# zeus 上这个 Recovery 的运行逻辑

## 1. 镜像里没有内核

```
skyward-zeus.img   104,857,600 B
├─ boot image header v0（header_size 1584）
├─ kernel      0 字节
├─ ramdisk     约 47 MB（LZ4 legacy，918 个条目）
└─ cmdline     512 字节全零
```

原厂 `OS3.0.3.0.VLBCNXM` 的 `recovery.img`（23,584,581 B ramdisk）同样 `kernel_size = 0`。
所以 recovery 分区只承载 ramdisk，内核由 bootloader 现场提供。

## 2. 引导链

```
系统里 reboot recovery
  └→ 往 misc 写 BCB：command = "boot-recovery"
       └→ ABL 读 misc，加载 boot_a 的【内核】+ recovery_a 的【ramdisk】
            └→ 现填 cmdline（androidboot.slot_suffix、serialno、build 指纹…）
                 └→ 内核解 initramfs，执行 /init
                      └→ /init 是符号链接 → system/bin/init（上游原厂 init 2,075,152 B）
                           └→ init.rc 的 recovery 域起 /system/bin/recovery
                                └→ 这个 9,294,752 B 的文件就是 skyward 本体
```

`fastboot reboot recovery` 无效（不发 BCB）；`fastboot boot` 也不适用于 100 MiB 的 ramdisk
（`Bad Buffer Size`）。每次进 rec 都要经系统写一次 BCB。

## 3. skyward 入口

`main()` 先看 `argv[0]`：init 用路径启动它，`basename == "recovery"` 时直接进 `recovery()`，
不解析子命令；终端里敲 `skyward info` 之类才走 clap。

`recovery()` 的固定顺序：

1. 建 `/run`（0755），保留上次日志
2. `sys.usb.config` 先 `none` 再 `adb`
3. 读 misc 的 BCB，判断本次是人工进入还是系统委托（更新 / fastbootd / 擦除 / Exit）
4. 读 `/skyward/device.toml`
5. 从 RTC 设时间（内核起来时钟是 1970）
6. CPU 频率切回系统档（否则待机空转耗电）
7. `prepare()`：super 经 dm-linear 映射，只读挂载 system / product / vendor / system_ext
8. `bring_up()`：ueventd 建节点 → logd → 原厂 services（按 prop 过滤）→ 固件 fallback
   → 挂 firmware 分区 → 挂其它分区 → `insmod` 模块 → 起 WLAN 预热线程 → 文件属主交接
   → 起 keymaster 程序（解 `/data` 的 FBE 用）
9. `ui::run()`：DRM/KMS 直出 1440×3200，evdev 取触摸，画首页

## 4. 驱动来自哪里

- 内核自带：msm_drm、evdev、USB gadget、dm-linear/dm-verity、erofs、f2fs/ext4、
  FBE 内联加密、binder、MHI/PCIe、cpufreq、RTC
- `/vendor`（`dm-5` erofs ro）与 `/vendor_dlkm`（`dm-6`）里共 319 个 `.ko` + `modules.dep`
- ramdisk 里另带 6 个音频 dlkm（原厂 rec 就在 early-init 里 insmod）

`.ko` 有 vermagic，必须与本机内核完全匹配；跨机型、跨内核借用会 `Invalid module format`。
这就是“驱动跟芯片绑定，不跟 Android 版本绑定”。

## 5. 两个硬件坑的根因

**震动**：`aw8697` 调 `request_firmware("aw8697_haptic.bin")`；`/vendor/firmware`、
`/vendor/firmware_mnt`、`/firmware` 三处都是 `sde7`（modem 分区 vfat），把 vendor 分区里真正的
固件遮蔽 → `-2 ENOENT` → 波形表空 → 听感“尖锐刺啦”。修法：把 3537 B 的固件放进
`system/etc/firmware/`（ramdisk 的 `/etc` 指向 `/system/etc`，ueventd 第一个搜索站）。

**WLAN**：`Assert WLAN_EN GPIO` → MHI → 首启校准 6.3 s → `cnss2` 每 ~56 ms 重试
“DMS QMI connection not established”共约 11.3 s → `Unable to get MAC from DMS` →
`hif_pci_enable_bus` → `MAC is all zero` → 用 `wlan_mac.bin` → supplicant。
首启 20.3 s，故 `INTERFACE_WAIT` 提到 45 s；再配合 `prewarm` 在开机就把芯片带起来，
页面初始为“关”，点亮开关 1~2 s 出列表。

## 6. 更新为什么是真刷分区

`updates` 拉 GitHub 最新 Release → `unzip`（zip 内只能有一个 `.img`）→ 读镜像内
`skyward/device.toml` 核对 `codename == "zeus"` → 算“下一启动槽 + 任何装着 Skyward 的槽”
→ 原样写 recovery 分区。没有备份环节，也没有 zeus 之外的包会被接受。
